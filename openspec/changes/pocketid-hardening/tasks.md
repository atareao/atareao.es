# Tasks: Endurecimiento del login PocketID (MP-03, MP-04, MP-05, MP-06, MP-07)

> **Nota inicial:** el repositorio no tiene framework de tests ni build tools. La verificación del change combina análisis estático (`just php-lint`, `just phpcs`), un **arnés de stubs externo** que vive solo en `/tmp/opencode/pocketid-harness/` (fuera del repo y no versionado) y E2E manual en producción con un PocketID real. El arnés no forma parte del commit ni del árbol. La implementación arranca **solo tras la aprobación del usuario**. Ninguna tarea renombra ni borra opciones, acciones de `wp-login.php` ni hooks. Objetivo rector: **una autenticación passwordless real, vinculada al proveedor y verificable**.

## 2. MP-03 — Passwordless real sin romper la publicación por REST

- [ ] 2.1 Aplicar el bloqueo de la **contraseña interactiva** en el punto común de autenticación (filtro `authenticate`) de modo que rechace las credenciales de `wp-login.php` sin depender de `$_POST['log']`/`$_POST['pwd']` ni de `wp-submit`/`action`, y cubra también XML-RPC. **Verificación:** arnés — con enforce activo, una autenticación interactiva con `$username`/`$password` válidos devuelve `WP_Error` aunque `$_POST` esté vacío. **Evidencia esperada:** arnés P03-1.
- [ ] 2.2 Cubrir XML-RPC por contraseña: con enforce activo, la autenticación por contraseña de usuario vía `xmlrpc.php` se rechaza. **Verificación:** arnés — invocación simulada de `wp.getUsersBlogs` con usuario/contraseña interactiva válidos sin `$_POST` devuelve error y no crea sesión. **Evidencia esperada:** arnés P03-2. **Depende de despliegue (config WP: XML-RPC habilitado/contraseñas locales).**
- [ ] 2.3 **PRESERVAR los Application Passwords y REST**: verificar que, con enforce activo, un Application Password válido sigue autenticando peticiones REST y permite publicar/editar contenido, y que el bloqueo no intercepta ni deshabilita `application_password_is_api_request`/`wp_authenticate_application_password`. **Verificación:** arnés — una petición REST simulada autenticada con Application Password se resuelve igual con enforce activo e inactivo; los filtros de application passwords no se alteran. **Evidencia esperada:** arnés P03-3. **Depende de despliegue (existencia y uso de Application Passwords reales).**
- [ ] 2.4 Preservar el login nativo (incluida la contraseña interactiva y XML-RPC) con la configuración incompleta o el modo exigir inactivo, y no afectar a `lostpassword`/`rp`/`postpass`. **Verificación:** arnés — sin enforce, el login interactivo y XML-RPC siguen autenticando; `postpass`/`rp` no se bloquean. **Evidencia esperada:** arnés P03-4/P03-5.
- [ ] 2.5 Documentar en el `README.md` que «Exigir PocketID» deshabilita la contraseña interactiva (formulario web y XML-RPC) pero **preserva** los Application Passwords y la publicación por REST. **Verificación:** `rg -n "Application Passwords|XML-RPC|passwordless" README.md` muestra la sección. **Evidencia esperada:** README actualizado.

## 3. MP-05 — Vinculación de identidad por `sub`

- [ ] 3.1 Extraer el claim `sub` de `userinfo` (o del `id_token` validado) y persistir la asociación `sub`↔usuario con `update_user_meta`/`get_user_meta`. **Verificación:** arnés — el primer login de un email existente guarda el `sub` y el segundo login con el mismo `sub` autentica sin depender del email. **Evidencia esperada:** arnés P05-1/P05-2.
- [ ] 3.2 Denegar con el 403 genérico cuando el `sub` no coincide con el previamente ligado a la cuenta resuelta por email, sin reasignar la cuenta. **Verificación:** arnés — un `sub` en conflicto no autentica y no altera la asociación previa. **Evidencia esperada:** arnés P05-3.
- [ ] 3.3 Comportamiento fail-safe si el proveedor no devuelve `sub`: no autenticar usando solo el email y denegar con el 403 genérico. **Verificación:** arnés — `sub` ausente → denegación. **Evidencia esperada:** arnés P05-4.
- [ ] 3.4 Mantener el rechazo de `email_verified` no verificado conforme a `atareao_pocketid_require_verified_email` (política estricta por defecto). **Verificación:** arnés — `email_verified=false` con política estricta → 403; con política laxa → continúa. **Evidencia esperada:** arnés P05-5. **Depende de despliegue (claims reales del IdP).**

## 4. MP-04 — `nonce` y validación del `id_token`

- [ ] 4.1 Añadir un parámetro `nonce` aleatorio (≥32 caracteres) a la petición de autorización, almacenado server-side junto al `state` (cookie + transient single-use) y consumido en el callback. **Verificación:** arnés — la URL de autorización contiene `nonce` y el callback lo consume una sola vez. **Evidencia esperada:** arnés P04-1.
- [ ] 4.2 Validar el `id_token` antes de confiar en él: firma contra el JWKS (`jwks_uri`) con algoritmo permitido, `aud` = `client_id`, `iss` = `issuer`, `exp` vigente con tolerancia acotada y `nonce` coincidente. Un `id_token` inválido no se persiste ni se usa. **Verificación:** arnés — firma inválida, `exp` expirado, `nonce` no coincidente y `aud`/`iss` erróneos se rechazan y no se almacenan. **Evidencia esperada:** arnés P04-2..P04-6.
- [ ] 4.3 Fallback razonado: si el proveedor no publica `jwks_uri` o el `id_token` no puede validarse, documentar por qué se acepta el `userinfo` sobre TLS y no tratar el `id_token` como prueba de identidad. **Verificación:** revisión del `README.md`/`design.md` con el razonamiento escrito; el `id_token` no se persiste. **Evidencia esperada:** decisión documentada.
- [ ] 4.4 Integrar la validación con el ciclo de vida del `id_token` para logout: solo un `id_token` validado se almacena y se usa como `id_token_hint`; si no hay uno validado, el logout local se completa sin error. **Verificación:** arnés — login con `id_token` inválido → no se guarda y el logout local funciona. **Evidencia esperada:** arnés P04-7.

- [ ] 6.2 Guardar el secreto en una opción con `autoload` desactivado y no devolverlo nunca al formulario, ni registrarlo en logs, ni incluirlo en exportaciones. **Verificación:** arnés — el HTML de Ajustes no contiene el secreto; el log no lo imprime; `autoload=no`. **Evidencia esperada:** arnés P07-2.
- [ ] 6.3 Mantener la validación `https://` de la URL y la restricción de host en la descarga del discovery (sin SSRF hacia otros hosts). **Verificación:** arnés — una URL no `https` o de otro host se rechaza/no se consulta. **Evidencia esperada:** arnés P07-3.
- [ ] 6.4 Documentar la precedencia de la constante/entorno y la no exposición del secreto en el `README.md`. **Verificación:** `rg -n "ATAREAO_POCKETID_CLIENT_SECRET" README.md` muestra la sección. **Evidencia esperada:** README actualizado.
